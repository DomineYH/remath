# Master Template을 학생·분석·멘토 세 템플릿으로 나눈다

목업의 스파인은 LLM 하나가 학생 대사·멘토 대사·`[CLASSIFICATION]` 블록을 한 응답에 내도록 짜여 있었지만, PRD 8절은 한 턴을 분석→학생→멘토 세 챗봇의 순차 호출로 정의하고 각자 다른 공급자·모델·effort를 허용한다. 그래서 스파인(`prompts/master.{en,ko}.md`)은 **학생 프롬프트 전용**으로 쓰고 분류·멘토 출력 규칙을 들어내며, 분석(`prompts/analysis.{en,ko}.md`)과 멘토(`prompts/mentor.{en,ko}.md`)는 짧은 전용 템플릿으로 둔다. 플레이스홀더는 새로 만들지 않고 목업의 집합을 세 템플릿에 나누어 배치한다(`CLS_TAIL`·`MENTOR_PREFIX`는 단일 프롬프트 전제여서 퇴역).

## Consequences

- 세 챗봇의 출력은 모두 **화자 접두 없는 본문**이다. 화자는 서버가 호출 단계로 안다. 분석 챗봇만 `[CLASSIFICATION]` 블록을 그대로 낸다.
- 멘토 LLM 호출은 **도움 요청(트리거 2)** 에서만 일어난다. 주도권 빼앗기(트리거 1)와 도달점(트리거 3)은 시나리오의 트리거 텍스트를 서버가 그대로 내보낸다.
- 세션 종료 리포트의 판정(clean/mixed/heavy 등)과 분류별 발화 목록은 **서버가 카운트로 계산**하고, 분석 챗봇은 요약 문장만 쓴다. 분류 기준이 없는 시나리오는 분석 템플릿을 컴파일하지 않으므로 분석 챗봇이 호출될 수 없다.
- 턴마다 바뀌는 진행 상태(오개념 카운터·도달 여부)는 게시 시점에 고정되는 컴파일 프롬프트의 플레이스홀더가 아니라, 호출 시 서버가 덧붙이는 **런타임 블록**으로 주입한다.
- 근거 티켓: [Spine 3분할 방식 결정](https://github.com/DomineYH/remath/issues/5).
